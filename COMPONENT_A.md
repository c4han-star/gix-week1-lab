# Component A — Staff interview synthesis

**Theme:** Asset return, checkout reconciliation, and BlueTally tracking after launch.

---

## Interview notes (organized from your session)

### 1. Current end-of-launch process

After launch (poster session + demos):

- All teams must return purchased items.
- Return happens at a **central table (3rd floor)** run by **you and Kevin**.
- Flow:
  1. Teams come to the table.
  2. Staff check a **master list** of items.
  3. For each item: ask **“Do you have this item?”** → if yes, collect it → mark it off the list.
  4. After collection, staff decide where items belong: **Makerspace**, **IT**, **neither (discard/other)**.
  5. Assign **asset type**, **location**, then add items into **BlueTally**.

### 2. Current system (BlueTally)

- Tracks **Assets** (unique items → barcode) vs **Accessories** (interchangeable → no barcode).
- Each asset has an **8-digit UW barcode** label.
- Entry can be manual or selected from records.
- Fields include **status** (e.g. ready to deploy) and **location** (IT shop, makerspace, etc.).

### 3. Check-in / check-out when students return

- Students check in with staff (you/Kevin).
- Staff look up **what they have checked out**, check items back into BlueTally.
- Then handle **newly purchased** returns: collect, label with barcode, add into system.

**Issue:** manual and slow; staff go **item-by-item twice** — once for **checked-out** items, once for **purchased returns**.

### 4. Pain points

| Area | Detail |
|------|--------|
| **Time** | Manual verification item-by-item; switching between checkout returns vs purchase returns; manual BlueTally entry. |
| **Workflow** | Barcodes often applied **only after return**; little tracking from **purchase** stage; duplicate work (check-in then re-enter). |
| **Reliability** | Items left unattended; missing items despite “returned”; complex kits (e.g. cameras) need manual verification. |
| **Decisions** | Makerspace vs IT vs discard is **manual**, **intuitive**, **not standardized**. |

### 5. Special cases

- **Small items:** if trackable → barcode on box; if interchangeable → log as accessories.
- **Accessories:** no individual tracking; **count-based** only (e.g. cables).

### 6. Ideas raised (for future systems / policy)

1. **Barcodes earlier** — assign at **purchase**, add to BlueTally immediately with team/project.
2. **Unified intake** — one workflow: scan everything; system distinguishes checkout vs new purchases.
3. **CSV / bulk upload** — pre-fill assets for large batches.
4. **UPC databases** — scan product UPC to auto-fill name/description/category.
5. **Standard routing rules** — reduce guesswork for Makerspace vs IT vs discard.
6. **Accountability** — direct handoff to staff; optional scan + timestamp confirmation.
7. **Kit tracking** — parent asset + component checklist for multi-part gear.

### 7. Bottleneck & recommendation (from discussion)

- **Bottleneck:** manual item-by-item intake + **delayed barcode assignment** + **double handling**.
- **If fixing one thing:** move **barcode assignment + system entry** to the **purchasing stage** to cut return time, reduce errors, and remove duplicate work.

> When **GIX staff running the post-launch asset return desk** needs to **reconcile checked-out equipment and newly purchased items against BlueTally**, they currently **verify and enter assets item-by-item at return time and often apply UW barcodes only after intake**, which causes **slow queues, duplicate handling, and errors such as missing pieces or unclear Makerspace-vs-IT routing**.
